# AgentProof architecture

Last audited: 2026-09-29

## Current system

AgentProof is currently a single Next.js application. It is a public product
concept and browser demo, not yet a multi-tenant service.

- **Framework:** Next.js 16.3.6 App Router, React 19, TypeScript in strict mode.
- **Styling:** Tailwind CSS 4 plus project CSS in `src/app/globals.css`.
- **Runtime:** the landing page is statically rendered; the directory route is
  a server route using the standard `Response` API.
- **Persistence:** none.
- **Authentication:** none.
- **External services:** none at runtime.
- **Testing:** Vitest, with lint, TypeScript, and tests composed by
  `npm run check`.

## Route inventory

### `GET /`

Implemented by `src/app/page.tsx`.

This is the existing launch landing page. It explains the proposed product and
contains the `IdentityDemo` client component. It has no account, dashboard, or
server-backed registration flow.

### `GET /.well-known/http-message-signatures-directory`

Implemented by
`src/app/.well-known/http-message-signatures-directory/route.ts`.

This is a hardcoded demonstration JWKS. It is not connected to an account or a
real signing key. It is intentionally retained during Phase 0 because this
phase may not change product behavior. Phase 3 must replace it.

## Browser identity lab

`src/components/identity-demo.tsx` currently:

1. Generates an extractable Ed25519 key pair with WebCrypto.
2. Exports public and private JWKs in the browser.
3. Calculates a SHA-256 RFC 7638 thumbprint from `crv`, `kty`, and `x`.
4. Shows a JWKS and request-header preview.
5. Signs an ad hoc local payload and verifies it against the same in-memory key.
6. Lets the developer download the private key bundle.

The lab does not upload key material. It also is not a protocol conformance
test:

- its claimed `https://id.agentproof.dev/<slug>` directory does not exist;
- that path is invalid for the default `directory` discovery type, which
  requires a bare origin;
- it does not construct the complete RFC 9421 signature base;
- its displayed signature uses base64url, while an RFC 8941 Byte Sequence uses
  standard base64 inside colons;
- it omits the `alg` and `nonce` parameters used by the current reference
  examples; and
- it verifies locally instead of asking an independent server verifier.

Phase 5 replaces this self-test. Until then, the UI correctly labels the lab as
experimental and says that generated identities are not persisted or
registered.

## Placeholder and incomplete behavior

- The hosted directory contains one fixed public key and cannot rotate or
  revoke it.
- The directory response is not signed and has no `Content-Digest`.
- The directory key declares JOSE `alg: "EdDSA"`; the current Web Bot Auth
  profile instead uses the HTTP Message Signatures algorithm name `ed25519`.
- There are no users, accounts, sessions, API keys, agents, challenges, or
  database tables.
- There is no proof-of-possession registration.
- There is no real signing SDK, CLI, independent verifier, telemetry, or audit
  log.
- `metadataBase` and lab URLs use `agentproof.dev`, but that domain is not
  configured in this repository or its Vercel project.

## Key custody invariant

Developers hold their own private keys. This is a system invariant, not a
feature flag.

1. Private keys are generated on the developer's machine by the browser, CLI,
   or SDK. They are never sent to AgentProof servers.
2. AgentProof stores only public Ed25519 JWK members: `kty`, `crv`, and `x`,
   plus public metadata such as a thumbprint.
3. Any server payload containing `d`, a private PEM, or another private-key
   representation must be rejected with HTTP 400. The server may log that a
   rejection occurred, but must never log the payload.
4. Endpoints handling keys must not log request bodies.
5. Registration requires a short-lived, single-use challenge signed locally.
   The server verifies proof of possession before storing a public key.
6. Directory response signatures are generated by the CLI or SDK and uploaded
   as attestations. The server verifies and stores them; it never signs as the
   developer.
7. AgentProof cannot observe normal requests signed locally and sent to third
   parties. Product analytics may use registrations, lifecycle changes,
   directory fetches, test verifications, and explicitly opt-in SDK telemetry
   only.

The Phase 0 route test recursively rejects private-key-shaped fields in the
current API response. When database migrations arrive, the guard test must be
extended to inspect every schema and key-bearing API response.

## Intended trust boundaries

- **Developer device:** trusted with private keys and signing operations.
- **AgentProof application:** trusted with account data, public keys,
  challenges, and verified public attestations only.
- **Database:** must never contain private key material or raw account API
  keys.
- **Verifier/origin:** independently chooses whether a valid identity is
  allowed. Authentication is not authorization or reputation.
- **Signature-Agent target:** untrusted network input to a verifier and an SSRF
  boundary. Future fetches require HTTPS, IP filtering, redirect rejection,
  byte limits, and timeouts.

## Planned module boundaries

The build plan adds capabilities in this order:

1. account and identity verification;
2. API keys and proof-of-possession agent registration;
3. database-backed directories and client-created attestations;
4. local CLI and SDK signing;
5. independent verification;
6. key lifecycle;
7. dashboard;
8. observable-event audit log; and
9. abuse controls.

No later phase may introduce managed private-key custody without a separate
security review.
